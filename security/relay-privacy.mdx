One of EvilChat's core design properties is that relays are dumb pipes. A relay operator running `GET /events` sees a stream of ciphertext blobs — not your messages, not your contacts, not who sent what to whom. This is not a policy promise; it is a structural property enforced by the protocol. The relay has no decryption keys, performs no signature verification, and applies no domain logic. This page gives you an honest, precise accounting of what a relay operator can and cannot observe, so you can make an informed decision about which relay to use — or whether to run your own.

## What Relays Can See

A relay operator with full access to the event log can observe the following for each envelope:

<Accordion title="Claimed AuthorDid (unreliable for DMs)">
  Every `SignedEnvelope` carries an `AuthorDid` field. The relay uses this for per-DID rate limiting but does **not** verify the signature — any DID string can be written into this field. For regular channel messages, the `AuthorDid` is the author's real device DID. For sealed-sender DMs (`Kind = Sealed`), the `AuthorDid` is a fresh per-message ephemeral DID that identifies no one.
</Accordion>

<Accordion title="StreamId (opaque routing key)">
  Each envelope carries a `StreamId` — a `Guid` used to route it. The relay stores and serves it as an opaque value; it does not contain a channel name or any human-readable information. For standard channels the ID is stable, so an operator who observes which DIDs write to which stream IDs can build a partial write-side graph over time. For sealed traffic (all DMs, and channels with the sealed policy) the `StreamId` is a **rotating epoch tag** derived from the conversation's MLS epoch secret — it changes at every epoch and is unlinkable across rotations, so no stable identifier ever appears on the wire.
</Accordion>

<Accordion title="Envelope size and timestamp">
  The relay records the byte size of each envelope and the server-assigned arrival offset (monotonic integer). The `Timestamp` field is author-asserted and display-only — the relay does not trust or order by it. Size and timing metadata are visible to the operator.
</Accordion>

<Accordion title="Identity-kind payloads (signed plaintext)">
  Envelopes of `Kind = Identity` carry signed plaintext by protocol design. This includes `IdentityAnnounced` (display name, seal public key, accent color), `DeviceAuthorized`, `DeviceRevoked`, and `KeyPackagePublished` events. These are intentionally readable — they form the public directory that lets peers verify each other before any session keys exist.
</Accordion>

## What Relays Cannot See

| Data | Why it's hidden |
|---|---|
| **Message content** | All non-`Identity` payloads are ciphertext. The relay has no keys. |
| **Who sent a DM** | Sealed-sender (`Kind = Sealed`) uses a fresh ephemeral signing key per message. The real sender's identity is inside the ciphertext, visible only to the recipient after decryption. |
| **Which DM (or sealed channel) a message belongs to** | Sealed traffic is addressed to rotating epoch tags. The relay cannot group a conversation's messages together across epochs, let alone attribute them. |
| **Who is reading** | Clients sync by polling `GET /events?since=<offset>` — a bulk scan by arrival offset. The relay cannot tell which streams a client is interested in from this query shape. |
| **Group membership changes** | MLS commits (member add/remove/update) are opaque TLS-serialized bytes — `Kind = Mls` in standard channels, and fully sealed envelopes in sealed channels, where the relay cannot even tell a membership operation happened. |
| **Channel names** | Channel IDs are opaque `Guid` values. No cleartext channel name appears on the wire. |
| **Reaction targets, edit content** | All message operations are inside encrypted payloads. The relay stores the blob; it cannot see what event type it is (aside from `Identity`). |

## Proving Relay Blindness

You can verify this yourself against a running relay:

```bash
curl -s 'http://localhost:5100/events?since=0' | jq
```

Examine the output. Each entry looks like:

```json
{
  "offset": 3,
  "envelope": {
    "eventId": "a1b2c3d4-...",
    "kind": 1,
    "authorDid": "did:evil:ABC123...",
    "timestamp": 1720000000,
    "streamId": "f47ac10b-...",
    "prevEventHash": "AAAA...==",
    "powNonce": 0,
    "payload": "7nK2pQr8...==",
    "signature": "xYz9..."
  }
}
```

The `payload` field on non-`Identity` envelopes is base64-encoded ciphertext. Only entries where `"kind": 0` (`Identity`) have a human-readable JSON payload — and those are the directory announcements that are deliberately public. Everything else is an opaque blob.

## Metadata Mitigations

EvilChat takes several steps to reduce the metadata visible even when you accept that some information is structurally observable:

<CardGroup cols={2}>
  <Card title="Opaque Stream IDs" icon="eye-slash">
    Channel IDs, inbox stream IDs, and the directory stream ID are all opaque `Guid` values. No cleartext channel name, user handle, or topic appears on the wire. A relay operator sees two DIDs writing to the same stream but not what that stream represents.
  </Card>
  <Card title="Sealed Sender for DMs" icon="envelope">
    Direct messages use a fresh ephemeral signing key per message. The relay cannot build a DM social graph — it cannot tell who is sending DMs to whom, only that some ephemeral key posted something to an inbox stream.
  </Card>
  <Card title="Bulk Sync (No Get-by-ID)" icon="database">
    Clients sync with a single `GET /events?since=<offset>` call. There is no per-stream or per-DID query API. The relay cannot distinguish which streams a client is following from its sync behavior.
  </Card>
  <Card title="Rotating Stream Tags" icon="arrows-rotate">
    Sealed conversations are addressed by a tag derived from the MLS epoch secret. Every epoch change — a member joining, a ban, a periodic ratchet update — rotates the tag, so the relay cannot correlate a conversation's traffic across epochs.
  </Card>
  <Card title="Sealed Channels (Opt-In)" icon="lock">
    Any channel can opt into sealed mode at creation. Its messages, its creation event, and even its membership commits ride ephemeral-signed sealed envelopes under rotating tags — the relay never sees the channel exist. See the sealed mode page for the full design.
  </Card>
</CardGroup>

## Rate Limiting and PoW

The relay's two anti-spam mechanisms — token bucket rate limiting and proof-of-work — are designed to work without learning who you are:

- **Rate limiting** is keyed by the claimed `AuthorDid` and applies only to non-sealed envelopes. Sealed envelopes are exempt: their ephemeral DIDs would each get a fresh, meaningless bucket, so the relay does not bucket them at all.
- **Proof-of-work** requires the sender to compute a nonce such that `SHA256(preimage ‖ signature ‖ nonce)` has enough leading zero bits. There are two tiers, advertised in `GET /info`: `PowBits` for standard envelopes, and a higher `PowBitsSealed` for sealed envelopes — the extra work replaces the rate limit the relay cannot apply to anonymous traffic. The cost is identical whether the signing DID is real or spoofed; it is purely computational friction, not identity-based.

The relay learns nothing about your identity from either mechanism that it does not already learn from the `AuthorDid` field.

## What Remains Visible

Honesty matters more than marketing here. Even with sealed mode everywhere, a relay operator still observes **timing, frequency, and size**: when envelopes arrive, how often, and how large they are. Sustained traffic analysis on those signals can suggest that *some* conversation is active, even if the operator cannot tell which one or between whom. Payload padding and cover traffic are open design areas, not shipped mitigations. Welcome deliveries also ride per-recipient inbox streams, so an operator can see that *someone* invited a given user to *something* at a point in time.

<Info>
  **Trust model:** If you self-host your relay, you are your own relay operator and the metadata above is visible only to you. If you use a shared or third-party relay, the operator can observe the metadata described in this page. The protocol does not require you to trust your relay operator for confidentiality of message content — but you should choose or run a relay whose operator you trust not to perform traffic analysis on the metadata that is visible. Running your own relay is the strongest option.
</Info>
