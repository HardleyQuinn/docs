EvilChat uses different encryption schemes tuned to the threat model of each message type — group channels, direct messages, key delivery, and long-term archiving each get a purpose-built layer. No single key protects everything. A compromised relay learns nothing. A compromised device key leaks only messages that key could decrypt. And your vault archive is ciphertext that only your device can open. This page explains each layer precisely, so you can reason about what an attacker at each position in the system can and cannot learn.

## Channel Encryption (RoomKey)

Standard channels use **AES-256-GCM** with a shared `RoomKey` — a 256-bit symmetric key distributed to channel members individually (see [Key Delivery](#key-delivery-ecies-sealed-box) below).

When the client encrypts a message, it uses the canonical envelope header fields as **AEAD associated data** (authenticated but not encrypted). This binds the ciphertext to its specific envelope: `EventId`, `Kind`, `AuthorDid`, `Timestamp`, `StreamId`, and `PrevEventHash` are all authenticated alongside the payload. A ciphertext extracted from one envelope cannot be replayed under a different header — the AEAD tag will not verify.

**v1 note:** RoomKey channels use a static key per channel (epoch 0). Key rotation is deferred to MLS. New channels that negotiate MLS get epoch-based rotation automatically.

<Accordion title="What AuthorDid verification looks like">
  After decryption, the client checks that the `AuthorDid` field inside the decrypted payload matches the verified signer on the `SignedEnvelope`. Any RoomKey holder can forge the payload `AuthorDid` field — the inner check against the envelope signature is the authoritative one. This is enforced before any domain event is dispatched to projections.
</Accordion>

## Channel Encryption (MLS)

For MLS-capable channels, EvilChat uses **RFC 9420 (Messaging Layer Security)** group encryption via the `evil-mls` Rust core (built on [OpenMLS](https://github.com/openmls/openmls)).

<CardGroup cols={2}>
  <Card title="Forward Secrecy" icon="shield-check">
    MLS uses epoch-based key ratcheting. Each commit (member add, remove, or update) advances the epoch and derives a fresh symmetric key. Old epoch keys are deleted, so a future key compromise cannot decrypt past messages.
  </Card>
  <Card title="Post-Compromise Security" icon="rotate">
    After a device is removed from an MLS group, the remaining members perform a healing commit that derives new key material the removed device cannot predict, even if it retained old secrets.
  </Card>
  <Card title="Member Addition (Welcome)" icon="user-plus">
    New members receive an MLS **Welcome** message — a sealed package containing the group's current state and epoch key — delivered via [ECIES sealed box](#key-delivery-ecies-sealed-box) so only they can open it.
  </Card>
  <Card title="Cryptographic Removal" icon="user-minus">
    Bans and removals are committed as MLS Remove proposals. The resulting commit ratchets the epoch, cryptographically ejecting the removed member. They cannot decrypt any traffic after their removal epoch.
  </Card>
</CardGroup>

MLS traffic envelopes use `Kind = Mls`. The relay cannot distinguish MLS application messages from handshake commits — both are opaque TLS-serialized `MLSMessage` bytes.

## Key Delivery (ECIES Sealed Box)

RoomKeys and MLS Welcome messages are delivered one-on-one using **ECIES** (Elliptic Curve Integrated Encryption Scheme):

1. The sender generates a fresh **ephemeral X25519 keypair**.
2. A shared secret is derived via **X25519 Diffie-Hellman** between the ephemeral private key and the recipient's **seal public key** (the `SealPublicKey` from their `IdentityAnnounced` event).
3. The shared secret is expanded through **HKDF-SHA-256** to produce an AES-256-GCM key and nonce.
4. The payload (RoomKey bytes or MLS Welcome) is encrypted with AES-256-GCM.
5. The ephemeral public key is prepended to the ciphertext so the recipient can re-derive the shared secret.

Only the holder of the recipient's Ed25519 identity key (which controls the corresponding X25519 key) can open the box. These envelopes use `Kind = KeySeal` and are addressed to the recipient's **inbox stream** — an opaque stream ID derived from their DID that other users can post to but only the recipient reads.

## Sealed-Sender DMs

Direct messages use **sealed sender** to hide the true author from the relay:

| Layer | Who signs | What the relay sees |
|---|---|---|
| Outer envelope | Fresh per-message **ephemeral** Ed25519 key | `AuthorDid` = ephemeral DID (identifies no one) |
| Inner payload | Your **real** device key | Your real DID + signature (decrypted by recipient only) |

The relay sees an `AuthorDid` it has never encountered before for every DM. It cannot correlate DMs to their senders, cannot build a social graph of who messages whom, and cannot apply per-sender rate limits to DMs (PoW serves as the spam deterrent instead). After the recipient decrypts the outer ciphertext, they verify the inner signature against the sender's real DID to authenticate the message.

Envelopes of `Kind = Sealed` trigger this path. The DM channel itself is a deterministic ID derived from both participants' DIDs, so only they know to watch that stream.

## Vault Re-Encryption

When the vault daemon archives events, the client performs a second layer of encryption specifically for long-term storage:

1. The client decrypts the incoming relay envelope using the appropriate session key (RoomKey or MLS epoch key).
2. It immediately re-encrypts the plaintext event under your **Storage Key** — a 256-bit AES-256-GCM key derived from your device and never transmitted anywhere.
3. The `nonce ‖ ciphertext+tag` blob is posted to the vault's `POST /archive` endpoint.

The vault stores only `(streamId, timestamp, nonce, ciphertext)` tuples. It never receives plaintext and never holds any key material. Even if your vault database is exfiltrated, the data is meaningless without your Storage Key.

**By design, the original relay ciphertext is permanently undecryptable.** Transient MLS epoch keys and RoomKey material are ephemeral. The vault holds the only long-term copy of decrypted events, and it is encrypted under your Storage Key.

<Note>
  **`Identity`-kind envelopes are a sanctioned exception.** Directory announcements (`IdentityAnnounced`, `DeviceAuthorized`, `DeviceRevoked`, `KeyPackagePublished`) are **signed plaintext** — the relay and any observer can read them. This is intentional: peers must be able to discover each other's seal public keys and verify device authority before any session keys have been established. Everything else — messages, reactions, edits, bans, RoomKeys, MLS traffic — is always ciphertext on the wire.
</Note>
