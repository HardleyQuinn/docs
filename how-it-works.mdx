EvilChat is built on the **EVIL** (Event Verified Immutable Ledger) protocol — a set of wire contracts and architecture rules that together guarantee end-to-end encryption, relay blindness, and convergent state across all clients. At its core, every piece of application state — a message, a reaction, an edit, a ban, a moderator grant — is an immutable signed event appended to a shared log. Relays store that log. Clients project it. No relay ever reads a message body, verifies an application-layer signature, or makes a decision based on content. The intelligence lives entirely at the edge.

## The Message Lifecycle

When you send a message in EvilChat, your client executes a precise pipeline before a single byte reaches the relay:

<Steps>
  <Step title="Create the domain event">
    EvilChat constructs a `MessageSentEvent` record containing your author DID, a new `EventId` (GUID), the channel ID, the message body, and an author-asserted Unix timestamp (used for display only — never for ordering).
  </Step>
  <Step title="Serialize and encrypt">
    The event is serialized to JSON and encrypted with the channel's AES-256-GCM RoomKey (or sealed inside an MLS application message for MLS channels). The resulting ciphertext becomes the `Payload` of a `SignedEnvelope`. The canonical envelope header (all fields except the PoW nonce) is used as AEAD associated data, so the ciphertext is bound to this exact envelope and cannot be replayed under a different header.
  </Step>
  <Step title="Sign the envelope">
    Your client signs the canonical preimage of the envelope with your Ed25519 private key and stores the 64-byte signature in the `Signature` field. The relay never checks this signature — that's the receiving client's job.
  </Step>
  <Step title="Stamp with proof-of-work">
    Your client iterates a `PowNonce` until `SHA256(preimage ‖ signature ‖ nonce)` has at least as many leading zero bits as the relay requires (advertised via `GET /info`). The nonce is excluded from the signature preimage, so mining never invalidates the signature.
  </Step>
  <Step title="POST to the relay">
    The complete `SignedEnvelope` is posted to `POST /events`. The relay checks the envelope's size, PoW difficulty, and your per-DID rate limit token bucket — nothing else. It assigns a monotonic arrival offset and stores the raw bytes.
  </Step>
  <Step title="Peers poll and decrypt">
    Other clients poll `GET /events?since=<last_offset>&limit=500` on their sync interval (~1.5 s in the demo). They receive the new envelope, verify the Ed25519 signature, decrypt the payload with the channel RoomKey, confirm the decrypted author DID matches the verified signer, and dispatch the domain event to their local projections.
  </Step>
</Steps>

## Relays Are Dumb Pipes

A relay's job is to be a high-availability append log, nothing more. The EVIL protocol is explicit: **relays run zero business logic**. The only checks a relay performs are purely mechanical, derivable from envelope bytes alone — no domain knowledge required:

| Check | What the relay verifies |
|---|---|
| **Size** | Envelope bytes ≤ `MaxEnvelopeBytes` (default 64 KiB). |
| **Parseability** | Bytes deserialize to a valid `SignedEnvelope` structure. |
| **Proof-of-work** | `SHA256(preimage ‖ signature ‖ nonce)` meets the configured leading-zero-bits target. |
| **Rate limit** | The per-`AuthorDid` token bucket (default: 30 capacity, 30 refill/min) has capacity. |

The relay does **not** verify Ed25519 signatures — it wouldn't know who to trust anyway. It does **not** filter by channel, recipient, or content. It does **not** perform get-by-id or filtered queries. The only read is bulk chronological sync by arrival offset (`GET /events?since=&limit=`), which means the relay never learns which channels or streams a client is interested in.

When you run the two-user demo, three resources start up:

| Resource | URL | Role |
|---|---|---|
| `relay` | http://localhost:5100 | Dumb pipe. Query `GET /info` to see its published parameters. |
| `client-alice` | http://localhost:5101 | Edge client, user **Alice** (owns `#general`). |
| `client-bob` | http://localhost:5102 | Edge client, user **Bob**. |

## Event Sourcing

EvilChat's entire application state is derived from an **append-only event log**. No event is ever mutated or deleted at the relay layer. When you delete a message, EvilChat appends a `MessageDeletedEvent` tombstone — the original `MessageSentEvent` stays in the log forever. When you edit a message, a `MessageEditedEvent` is appended; projections display whichever edit has the highest `(Timestamp, EventId)`, a deterministic total order that ensures every client converges to the same result regardless of the order in which they receive events.

Three projection rules underpin EvilChat's convergence guarantees:

- **Park, don't drop.** If an `Encrypted` or `Mls` envelope arrives before the client has the RoomKey (e.g., a `KeySeal` is in flight), the ciphertext is stored in a parking lot and replayed automatically once the key lands. Projections converge regardless of arrival order.
- **Cursors advance by relay offset.** Clients never use author-asserted timestamps for ordering — those are display hints only. The relay's monotonic offset is the authoritative sequence.
- **Authority is resolved at query time.** Ban and moderator-grant events can arrive out of order; the projection re-evaluates authority (keyed-maximum per `(channel, target)` among events whose author holds valid authority) every time it answers a query. A grant that arrives after a ban still applies retroactively.

## Envelope Kinds

Every `SignedEnvelope` carries a `Kind` field that tells the receiving client how to process the payload. Relays store all kinds identically — the distinction is purely for the edge.

| Kind | Name | Purpose |
|---|---|---|
| `0` | `Identity` | Signed **plaintext** directory event (`IdentityAnnouncedEvent`, `KeyPackagePublishedEvent`, device authorization/revocation). The only sanctioned exception to ciphertext-only — peers must be discoverable before any session keys exist. |
| `1` | `Encrypted` | Domain event encrypted with the channel's AES-256-GCM **RoomKey** (Sender Key model). Used for channel messages, reactions, edits, deletions, and channel creation on non-MLS channels. |
| `2` | `KeySeal` | RoomKey material sealed 1-on-1 to a single recipient using ECIES (the recipient's X25519 `SealPublicKey`). Addressed to the recipient's inbox stream. Contains `RoomKeyDistributedEvent` or `MlsWelcomeEvent`. |
| `3` | `Mls` | MLS traffic on a channel stream: both application messages (domain events inside) and handshake commits. Your client distinguishes them during MLS processing. Used for new channels with full MLS group encryption. |
| `4` | `Sealed` | **Sealed-sender** envelope for DMs. The outer envelope is signed by a fresh per-message ephemeral key (`AuthorDid` is that ephemeral key and authenticates no one). The real author DID, their Ed25519 signature, and `PrevEventHash` live inside the ciphertext and are verified post-decrypt. The relay cannot see who sent a DM. |

<Note>
  The mandatory client pipeline is **Verify → decrypt → bind → dispatch**. Envelope signatures are checked first; after decryption, the payload's `AuthorDid` field must match the verified signer before the event is dispatched to any projection. This matters because any RoomKey holder could forge payload fields — the protocol closes that gap by anchoring author identity to the envelope signature, not the decrypted JSON.
</Note>

## The Vault

The `evilvault` daemon is an optional, self-hosted personal archive. Because transient message keys (RoomKeys, MLS epoch keys) make archived relay ciphertext permanently undecryptable by design, the vault works differently: your EvilChat client decrypts incoming messages as normal and then **re-encrypts the plaintext under a Storage Key you control** before sending records to the vault over its local HTTP API (`POST /archive`).

The vault stores only what your client sends it — it never connects to a relay, never holds your keypair, and never performs any decryption. Auth is a bearer token minted during `evilvault init` and stored in `~/.config/evilvault/config.json` (or `%AppData%\evilvault\config.json` on Windows). You can rotate the token at any time with `evilvault token rotate`.
