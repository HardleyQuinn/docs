`evilvault` is a lightweight daemon you run on your own machine or server. The EvilChat client decrypts incoming events using your session keys (RoomKey or MLS), re-encrypts them under your long-term Storage Key (AES-256-GCM), and sends them to the vault — giving you a permanent, tamper-evident archive that the vault itself cannot read. Because only your device ever holds the Storage Key, even a compromised vault host learns nothing about your message history.

## How It Works

The vault fits into the EvilChat architecture at the archival layer — after end-to-end decryption, before long-term storage:

<Steps>
  <Step title="Receive and decrypt">
    The EvilChat client polls the relay and collects signed envelopes for your streams. Encrypted envelopes (`Kind: 1–4`) are decrypted locally using the appropriate session key: a RoomKey for channel messages, your MLS group state for MLS traffic, or your private key for key-sealed DMs.
  </Step>
  <Step title="Re-encrypt under Storage Key">
    The client re-encrypts each decrypted domain event using your Storage Key (a local AES-256-GCM key). A fresh 12-byte random nonce is generated per record. The result is `(nonce ‖ ciphertext+tag)` — the vault stores these two fields but never the plaintext or any key material.
  </Step>
  <Step title="POST /archive">
    The client sends a batch of `VaultRecord` objects to `POST /archive` on the running vault daemon. The vault performs an `INSERT OR IGNORE` on `eventId`, so re-sending already-archived records is safe and idempotent.
  </Step>
  <Step title="Hydrate history">
    When you open a channel or DM that your vault has archived, the client calls `GET /archive?streamId=<uuid>` to retrieve stored records, decrypts them with the Storage Key, and renders the message history — even if those events have since been purged from the relay.
  </Step>
</Steps>

The vault stores exactly five fields per record: `eventId`, `streamId`, `timestamp`, `nonce`, and `ciphertext`. It holds no plaintext, no session keys, no relay envelopes, and no decryption capability.

## API Authentication

All vault HTTP endpoints require a bearer token in the `Authorization` header:

```http
Authorization: Bearer <token>
```

The token is a 48-character lowercase hex string (24 random bytes) generated by `evilvault init` and stored in `config.json`. Rotate it at any time with `evilvault token rotate` — the old token becomes invalid on the next daemon restart. After rotating, update the token in EvilChat under **Settings → Vault**.

## Base URL

The vault daemon listens on:

```
http://localhost:5200
```

by default. Change the port with `evilvault config set port <n>` or by setting the `EVILVAULT_PORT` environment variable before starting the daemon. The EvilChat client reads the vault URL from **Settings → Vault**.

## Endpoints

| Method | Path | Purpose |
|--------|------|---------|
| `POST` | `/archive` | Batch upsert of `VaultRecord` objects |
| `GET` | `/archive` | Range query of archived records by stream and time window |
| `GET` | `/status` | Daemon health check, record count, and database size |

For full parameter and response documentation, see the [HTTP API reference](/api/vault-api).

<Warning>
  **Back up your Storage Key and data directory.** If the Storage Key is lost, every archived record becomes permanently inaccessible — there is no recovery path, because the vault itself never holds the key. The Storage Key lives alongside your vault database in the data directory (`~/.config/evilvault/data/` by default on macOS/Linux). Back up the entire `.data/` directory, including `vault.db`, to a secure location.
</Warning>
